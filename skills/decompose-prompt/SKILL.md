# Decompose Prompt

Обёртка над главной (и единственной) LLM-операцией проекта: транскрипт → задачи в JSON.
Всё остальное в пайплайне — детерминированный код. Здесь — языковое суждение модели.

## Модель и доступ

- Модель: **Qwen 3 32B**. На тесте — через Groq или OpenRouter (бесплатно).
  В проде — локально через Ollama/vLLM. Те же веса, поведение переносимо.
- Доступ — через OpenAI-совместимый клиент. Провайдер за конфигом (`base_url` + `model`),
  чтобы переключение тест→локаль было сменой одной строки.
- Ключ — в окружении, не в коде.

## Системный промпт

Системный промпт лежит в файле проекта `CLAUDE.md` (он же system prompt декомпозиции).
НЕ дублировать его содержимое здесь — читать из файла и передавать как `system` сообщение.
Промпт задаёт: что считать задачей, grounding (привязка к источнику), формат JSON,
правила против выдуманных чек-листов, путь «задач нет», опциональные якоря.

## Вызов

1. Прочитать системный промпт из `CLAUDE.md`.
2. Передать транскрипт как user-сообщение.
3. Запросить ответ. Для длинных транскриптов — обрабатывать частями (промпт это учитывает).
4. Получить ответ: массив JSON задач + после `---` сводка и блок «что не взято».

## Парсинг ответа

- Извлечь JSON-массив из ответа (до маркера `---`).
- Распарсить. Если парсинг падает (модель обернула в текст/markdown) — повторить запрос
  с напоминанием «только чистый JSON», максимум N раз.
- Пустой массив `[]` — ВАЛИДНЫЙ результат («задач нет»), не ошибка.

## Что НЕ делает этот скилл

- НЕ сопоставляет имена с YouGile ID (это people-lookup, код).
- НЕ парсит якоря (это anchor-parser, код, до LLM).
- НЕ валидирует grounding/даты (это валидаторы, код, после LLM).
- НЕ пишет в трекер.

Этот скилл — только вызов модели и парсинг её ответа. Вход: чистый транскрипт (возможно,
с разметкой якорей от anchor-parser). Выход: список задач-кандидатов в JSON для валидаторов.

## Структура задачи на выходе

См. формат в `CLAUDE.md` (раздел «Формат задачи»). Ключевые поля: title, description,
checklist, acceptance_criteria, assignee (имя), controller (имя), due_date, priority,
source (обязательно, grounding), anchor_used, confidence, needs_review.
Поле validator_flags добавляет НЕ модель, а валидатор после.

## Замер (E0)

На этапе замера логировать для каждого прогона: вход, ответ модели, число задач,
сколько с низким confidence, режим (с якорями / без). Из этих логов считаются два числа
go/no-go. Без структурного лога замер придётся делать руками.
