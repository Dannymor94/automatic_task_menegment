# Pipeline Conventions

Единые правила для всех компонентов проекта. Следовать при разработке каждого шага.

## Главный принцип

**Детерминизм у ядра, LLM — в одной точке.** Чем ближе к сути, тем больше кода и меньше
свободной генерации. LLM вызывается ровно один раз (декомпозиция, см. decompose-prompt).
Всё остальное — детерминированный Python: regex, lookup, валидаторы, вызовы API.

Если ловишь себя на желании «добавить ещё один LLM-вызов, чтобы что-то поправить» — стоп.
Скорее всего, это делается кодом. Новый LLM-вызов = новая точка галлюцинаций.

## Порядок шагов

```
1. Транскрипция        аудио → текст (Whisper, faster-whisper, локально)
2. Нормализация        текст → сегменты [id, speaker, ts, text]
3. Парсинг якорей      regex + нечёткое совпадение (ASR-искажения). Якоря ОПЦИОНАЛЬНЫ
4. People lookup       имя → YouGile user ID по справочнику (детерминированно)
5. Декомпозиция        LLM: транскрипт → задачи JSON (единственный LLM-шаг)
6. Валидация           grounding, проверка дат, флаги. Ставит validator_flags
7. [ПАУЗА: ревью менеджером]
8. Запись в YouGile    идемпотентно (см. yougile-integration)
```

## Двухфазность (критично)

Ревью разрывает пайплайн. Не делать сквозной прогон до записи.
- **Фаза 1** (авто): шаги 1–6. Финальный статус `awaiting_review`.
- **Пауза**: менеджер ревьюит каждую задачу, правит, одобряет.
- **Фаза 2** (по одобрению): шаг 8. Только одобренные задачи.
Состояние созвона хранится между фазами (в памяти на E0–E1, в Postgres на E2+).

## Валидаторы ставят флаги (не LLM)

Подсветка рисков на ревью — по детерминированным флагам валидатора, НЕ по LLM-confidence
(самооценка модели ненадёжна). Валидатор проверяет и ставит `validator_flags`:
- `due_invented` — due_date есть, но в source-фрагменте нет даты/временного выражения.
- `assignee_unmatched` — имя не найдено в справочнике людей.
- `no_grounding` — поле source пустое или ссылается в никуда.
Поле с флагом → подсвечивается менеджеру. confidence модели — вторичная подсказка.

## Логирование

Каждый шаг логирует: вход (кратко), выход (кратко), время, успех/ошибка.
LLM-шаг особо: промпт, ответ, число задач, число с низким confidence, режим (якоря/без).
На E0 логи — инструмент замера (из них два числа go/no-go). Формат:
- E0–E1: модуль `logging` в файл (структурно, желательно JSON-строки).
- E2+: таблица логов в Postgres.

## Идемпотентность

Любая запись во внешнюю систему (YouGile) — идемпотентна. Повторный запуск не плодит дубли.
Хранить соответствие «внутренний id задачи ↔ YouGile task id», маркер ставить после успеха.

## Ретраи

Внешние вызовы (Whisper API, LLM API, YouGile) оборачивать в ретрай с backoff.
Различать: временный сбой (повторить) vs фатальная ошибка данных (остановить, залогировать).

## Путь «задач нет»

Пустой результат декомпозиции (`[]`) — нормальный исход (созвон-вода). Не считать ошибкой,
не пытаться выжать задачи. Пайплайн завершается со статусом «задач не найдено».

## Чего не делать

- Не добавлять LLM-вызовы для детерминируемых операций.
- Не писать в трекер до одобрения (фаза 2).
- Не выдумывать чек-листы/критерии (см. CLAUDE.md).
- Не строить confidence-подсветку на самооценке модели.
- Не усложнять оркестратор раньше времени: Python-слой на старте, Celery — только при потоке.
