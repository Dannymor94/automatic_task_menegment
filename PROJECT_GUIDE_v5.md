# Созвон → Задачи: система снятия операционки с менеджера

> v5.0 — документ под реальную задачу. Веб-приложение.
> Менеджер ведёт несколько команд/проектов; после созвона задачи автоматически уходят
> в нужный трекер с исполнителем, контролёром, сроком и описанием — после ревью менеджером.

---

## 1. Задача

Менеджер ведёт созвоны с разными командами (разные проекты, разные трекеры) + личные проекты.
Сейчас после каждого созвона он вручную заводит задачи в трекеры, назначает людей, ставит сроки.
Это рутина и операционка, которую и снимает система.

**Вход:** аудио созвона (или готовый транскрипт).
**Выход:** задачи в YouGile (нужный проект) — с исполнителем, контролёром, сроком, описанием.
**Условие:** менеджер ревьюит **каждую** задачу до отправки. Система готовит — менеджер утверждает.

**Трекер:** YouGile (один, несколько проектов внутри), запись через REST API.
**Интерфейс:** своё веб-приложение (загрузка + ревью), пишет в YouGile через API. Два разных
приложения: твой интерфейс и YouGile.

---

## 2. Схема (твоя, уточнённая)

```
Своё веб-приложение (загрузка)
   → [ОРКЕСТРАТОР ведёт пайплайн, состояние и логи]
        → Аудио
        → Транскрипция (Whisper)
        → Детерминированные скрипты (нормализация + якоря + lookup людей + маршрут проекта)
        → LLM (декомпозиция в задачи с привязкой к источнику)
        → Валидация скриптами (grounding, даты, дубли, подстановка YouGile user ID)
        → [ПАУЗА: ревью менеджером — пайплайн ждёт человека]
        → Запись в YouGile (REST API, идемпотентно: задача + стикеры)
```

**Двухфазность.** Ревью разрывает пайплайн на две фазы. Фаза 1 (автоматика): шаги до ревью,
статус `awaiting_review`. Фаза 2 (по одобрению): запись в YouGile. Оркестратор умеет
остановиться, дождаться человека и продолжить — это не один сквозной прогон.

Детерминизм обрамляет LLM с двух сторон: скрипты готовят чистый вход и проверяют выход.
LLM отвечает только за языковое суждение (что есть задача, как её сформулировать).

## 2а. Оркестратор

Дирижёр пайплайна: запускает шаги по порядку, ведёт состояние каждого созвона, логирует,
повторяет при сбоях. Растёт вместе с проектом — простой на старте, очередь задач позже.

**Обязанности:**
1. **Пайплайн** — вызвать шаги по порядку, передать результат одного на вход следующего,
   остановиться при фатальной ошибке.
2. **Состояние** — для каждого созвона: текущий шаг, успех/ошибка, результат. Питает статус
   в веб-интерфейсе (транскрибируется / разбирается / готово к ревью / записано).
3. **Логирование** — каждый шаг: вход, выход, время, успех/ошибка. Для LLM-шага особо:
   промпт, ответ, сколько задач, сколько с низким confidence. Это сырьё для двух чисел замера.
4. **Ретраи** — повтор шага при временном сбое внешних API (Whisper, LLM, YouGile).
5. **Идемпотентность записи** — повторный запуск НЕ создаёт дубли в YouGile. Каждая
   отправленная задача помечается; повтор пропускает уже записанные. Критично: запись
   в трекер необратима и видна команде.

**Двухфазность** (см. схему): оркестратор останавливается на `awaiting_review`, ждёт
одобрения менеджера, затем запускает фазу записи. Состояние хранится между фазами.

**Реализация по этапам (не усложнять преждевременно):**

| Этап | Оркестратор | Логи | Очередь/ретраи |
|---|---|---|---|
| E0–E1 | тонкий слой на Python (функция-пайплайн) | модуль `logging` в файл | try/except + повтор |
| E2–E4 | класс со state-machine, состояние в Postgres | структурные логи в Postgres | в коде |
| E5+ | Celery + Redis (при потоке многих созвонов) | централизованно | очередь задач |

Полноценный оркестратор (Temporal/Airflow) на старте — избыточен: пайплайн линейный,
нагрузки нет. Вводится только когда появятся параллельные созвоны и реальная нагрузка.

## 3. Проблемы: что решено, что осталось

### 3.1 Маршрутизация — упрощена (один трекер)
Трекер один (YouGile), внутри несколько проектов. Маршрут = выбор проекта/доски, не трекера.
Задаётся якорем `ПРОЕКТ <название>` в начале созвона или выбором в форме загрузки. Просто.

### 3.2 Идентификация людей — решена справочником
Имена уникальны (поддерживаются в справочнике). Справочник «имя → YouGile user ID → роль».
Якорь даёт имя → скрипт-lookup подставляет user ID. Детерминированно, без угадывания и тёзок.
Условие: новый человек заводится в справочник; реальных тёзок различаешь именами (Дима П. / Дима С.).

### 3.3 Качество извлечения — ГЛАВНЫЙ риск, не решён, проверяется замером
Снимет ли система рутину, зависит от того, насколько хороши задачи из реального созвона.
Якоря резко повышают точность, но насколько — неизвестно до прогона реальных записей.
**Проверяется первым (этап 0), до любой разработки.** Всё остальное вторично к этому числу.

## 3а. Правила против мусора (заложены в ядро)

Цель — снять работу с менеджера, а не добавить вычитку машинного мусора. Поэтому:

**Не выдумывать чек-листы и критерии приёмки.** На созвоне обычно нет ни подшагов, ни критериев
приёмки — если их генерировать всегда, модель их придумает, и менеджер будет удалять выдуманное
на ревью. Правило: `checklist` и `acceptance_criteria` заполняются **только если реально
прозвучали** в транскрипте. Иначе — пусто. Дожать чек-лист можно опционально, по явному запросу
менеджера, а не автоматически.

**Подсветка рисков — по детерминированным флагам, не по LLM-confidence.** Самооценка модели
ненадёжна (модели уверенно ошибаются). Поэтому на ревью поля подсвечиваются по проверкам
валидатора (код), а не по `confidence` модели:
- даты нет в источнике → флаг «срок выдуман»;
- имя не найдено в справочнике → флаг «исполнитель не опознан»;
- нет привязки к источнику → флаг «нет grounding».
LLM-confidence остаётся вторичной подсказкой, не основой.

**Путь «задач нет» — нормальный исход.** Реальные созвоны на 40–60% — вода и оффтоп. Если из
каждого выжимать задачи, система начнёт галлюцинировать из пустого. Поэтому «в этом фрагменте
задач нет» — допустимый и ожидаемый результат, не ошибка.

**Обновления существующих задач — честная граница.** Созвоны часто про уже существующие задачи
(«по лендингу сдвигаем срок»). Но надёжное сопоставление с задачей в YouGile требует
семантического поиска (вектора), потому что названия не совпадают дословно. Решение:
- **На старте (E1–E5) система только СОЗДАЁТ задачи.** Реплики-обновления распознаются и
  показываются менеджеру как «похоже на обновление существующей», но автоматически не применяются.
- **Полноценные обновления — на E6**, вместе с Qdrant (семантический поиск задачи).
Это честно: не обещаем работающие обновления без механизма, который их обеспечивает.

## 4. Якоря — опциональный усилитель (не обязательное условие)

**Программа работает и без якорей.** Якоря — способ повысить точность, но не требование.
Логика всегда пытается извлечь задачи из обычной речи; якоря, если звучат, дают явный сигнал
и поднимают уверенность. Это снимает главный поведенческий риск: не нужно дисциплинированно
проговаривать якоря на каждом созвоне, чтобы система работала.

| Якорь | Что задаёт |
|---|---|
| `ПРОЕКТ …` | маршрут: проект/доска в YouGile |
| `ЗАДАЧА …` | создать задачу |
| `ИСПОЛНИТЕЛЬ …` | кто делает |
| `КОНТРОЛЬ …` | кто проверяет |
| `СРОК / ДЕДЛАЙН …` | срок |
| `ПРИОРИТЕТ …` | важность |
| `ГОТОВО / СДВИГ / БЛОК …` | обновить существующую задачу |

Якорь ловит детерминированный скрипт (regex) — отсюда надёжность. Есть якорь → высокая
уверенность, поле берётся почти как есть. Нет якоря → LLM извлекает из обычной речи,
поле помечается на ревью.

**Замер обоих режимов (E0):** качество меряется отдельно с якорями и без. Если без якорей
приемлемо — якоря бонус. Если без якорей разваливается — проект зависит от дисциплины
проговаривания, и это надо знать заранее.

Опциональная **инструкция менеджеру** объясняет, как проговаривать якоря для лучшего результата —
но это рекомендация, а не условие работы.

## 5. Веб-приложение (интерфейс)

Один интерфейс на загрузку и ревью.

| Экран | Назначение |
|---|---|
| **Загрузка** | Перетащить аудио/транскрипт, выбрать проект (или взять из якоря `ПРОЕКТ`) |
| **Обработка** | Статус: транскрибируется / разбирается / готово к ревью |
| **Ревью** (главный) | Карточки задач-черновиков; правка inline; поля под сомнением подсвечены; источник по клику; одобрение каждой |
| **Справочники** | Проекты → трекеры → люди → аккаунты. Настройка маршрутов |
| **История** | Прошлые созвоны, что ушло в трекеры |

**Экран ревью — рабочее место.** Каждая задача = карточка:
- Подсвечены рискованные поля по **флагам валидатора** (срок выдуман / исполнитель не опознан /
  нет grounding) — не по самооценке модели.
- Клик по полю → фрагмент транскрипта-источника (grounding).
- Inline-правка, кнопка одобрения. Запись в YouGile — только по одобрению.
- Пустые чек-лист/критерии — норма (не выдуманы). Кнопка «дожать чек-лист» по желанию.

## 6. Внутренний формат задачи → YouGile

```json
{
  "project": "проект/доска в YouGile (определяет маршрут)",
  "title": "с глагола",
  "description": "контекст 1-2 предложения",
  "checklist": ["подшаг"],
  "acceptance_criteria": ["критерий готовности"],
  "assignee": "YouGile user ID или null",
  "controller": "YouGile user ID или null",
  "due_date": "YYYY-MM-DD или null",
  "priority": "low|medium|high|urgent",
  "source": "фрагмент транскрипта (обязательно)",
  "anchor_used": true,
  "confidence": 0.0,
  "validator_flags": ["due_invented", "assignee_unmatched", "no_grounding"],
  "needs_review": true
}
```

`validator_flags` ставит **детерминированный валидатор** (код), не модель — это основа подсветки
на ревью. `confidence` от модели — вторичная подсказка.

**Маппинг в YouGile (через REST API v1):**
- Структура совпадает: компания → проекты → доски → колонки → задачи. Маршрут = проект/доска.
- `assignee` → стикер «Исполнитель» (YouGile user ID).
- `controller` → кастомный текстовый стикер «Контролёр» (заводится один раз).
- `due_date` → стикер «Дедлайн».
- `priority` → стикер «Приоритет».
- `checklist` → подзадачи / чек-лист в чате задачи.
- `description` → описание задачи.
- Удобно: если стикера или его состояния нет — YouGile создаёт автоматически.

**Идентификация людей:** справочник «имя (уникальное) → YouGile user ID → роль». Якорь даёт
имя, скрипт-lookup подставляет user ID. Имена уникальны (поддерживается вручную в справочнике),
поэтому сопоставление детерминированное, без угадывания. Роль задаётся якорем в моменте
(`ИСПОЛНИТЕЛЬ` / `КОНТРОЛЬ`), имя только идентифицирует человека.

## 7. Стек

| Слой | Выбор |
|---|---|
| Веб (фронт) | React |
| Бэкенд | FastAPI (Python) |
| БД (справочники, история) | PostgreSQL |
| Транскрипция | Whisper (faster-whisper, локально) |
| LLM | Qwen 3 32B — по API (Groq/OpenRouter) на тесте, локально (Ollama/vLLM) в проде |
| Детерм. слой | Python-скрипты: парсинг якорей, валидаторы, сопоставление людей |
| Оркестратор | E0–E1: Python-слой + logging; E2–E4: state-machine + Postgres; E5+: Celery + Redis |
| Адаптер трекера | Клиент YouGile REST API (задача + стикеры) |
| Дедупликация | векторный поиск (Qdrant) — позже |

LLM за абстракцией (OpenAI-совместимый `base_url`): тест по API → прод локально без смены
модели. Целевое железо для локали: NVIDIA 24 ГБ + 64 ГБ RAM (Qwen 32B).

## 8. Этап 0 — ЗАМЕР (до разработки)

Не строить веб, пока не доказано ядро. Минимум:
1. Ключ Groq/OpenRouter (Qwen 3 32B).
2. Промпт декомпозиции (CLAUDE.md / system prompt) с grounding; якоря опциональны.
3. 10–15 реальных транскриптов своих созвонов. Часть — с проговоренными якорями, часть — без.
   Желательно включить «водянистые» созвоны (оффтоп) — проверить путь «задач нет».
4. Прогнать скриптом, оценить глазами.

**Что меряем:**
- **% корректных задач** (годных / мусор / пропущено) — **отдельно с якорями и без якорей**.
  Это ключевое: показывает, работает ли система на обычной речи или зависит от дисциплины якорей.
- **Время ревью** vs ручное заведение в трекер.
- **Поведение на воде:** на оффтопных фрагментах система говорит «задач нет», а не выдумывает?

**Go/no-go.**
- Без якорей качество приемлемо, ревью быстрее ручного → строим веб (E1+), якоря бонус.
- Только с якорями приемлемо → работает, но зависит от дисциплины проговаривания (знать заранее).
- Плохо в обоих режимах или много выдумок на воде → чиним промпт или пересматриваем.

## 9. Дорожная карта

| Этап | Результат |
|---|---|
| **E0. Замер** | Скрипт + Qwen + 10–15 транскриптов → 2 числа, go/no-go |
| **E1. Ядро пайплайна** | Оркестратор-слой (Python+логи) гоняет: транскрипция → якоря → LLM → валидация → JSON (без UI) |
| **E2. Справочники + маршрут** | БД проектов/людей, справочник имя→YouGile ID, якорь ПРОЕКТ, lookup; состояние созвона в Postgres |
| **E3. Запись в YouGile** | Идемпотентная запись (задача + стикеры) после подтверждения; маркер «отправлено» |
| **E4. Веб-ревью** | Экран загрузки + ревью; двухфазность: фаза 1 авто → пауза → фаза 2 запись по одобрению |
| **E5. Полировка маршрута** | Несколько проектов, маршрутизация по якорю/форме, обработка ошибок API. **До E6 — только создание задач** |
| **E6. Обновления + контроль** | ГОТОВО/СДВИГ/БЛОК через семантический поиск задачи (Qdrant); напоминания контролёру |
| **E7. Приватность** | Qwen 32B локально после апгрейда железа |

Критический путь: **E0 → E1 → E3 → E4** (минимальный сквозной продукт: созвон → ревью → YouGile).

## 10. Границы честности

- **Главный риск — качество извлечения.** Не проверено ни на одной реальной записи. Всё
  остальное вторично к этому числу. E0 обязателен.
- **«Рутина менеджера» шире создания задач:** обновление существующих, контроль сроков,
  напоминания. Создание — только часть. Полное снятие операционки требует E6.
- **Уникальность имён — это работа, не данность.** Справочник надо вести; новый человек →
  завести; реальных тёзок различать именами. Без этого lookup ломается.
- **Назначение в YouGile слепым автоматом недопустимо** — ошибку видит вся команда.
  Поэтому ревью каждой задачи — требование, не опция.
- **Идемпотентность записи обязательна.** Повторный запуск после сбоя не должен дублировать
  задачи в YouGile. Каждая отправленная помечается; без этого перезапуск плодит дубли у команды.
- **Логи на E0 — не формальность, а инструмент.** Из них считаются два числа замера; без
  структурного лога LLM-шага (сколько задач, какой confidence) замер придётся делать руками.
- **Запись созвонов** требует согласия участников (юридически). Решить до использования.
- LLM по API на тесте = данные уходят провайдеру; приватность — на локали (E7).
